# نبض · Nabḍ

لوحة عربية لإدارة حملات إشعارات تطبيقات الموبايل، مبنية بـ Next.js وTypeScript وSQLite. تتضمن حساب مدير، مسودات، جدولة، استهداف Android/iOS والشرائح، معاينة الإشعار، تسجيل الأجهزة، وسجل طلبات الإرسال.

## التشغيل

يتطلب Node.js 24 أو أحدث.

```sh
npm ci
npm run dev
# في عملية أخرى، من نفس مجلد المشروع:
npm run worker
```

افتح المنفذ 3000 وأنشئ حساب المدير من `/setup`. لا يوجد حساب افتراضي أو كلمة مرور ثابتة. جهّز الحساب قبل إتاحة الخادم على الإنترنت؛ أول مستخدم يفتح صفحة الإعداد يمكنه إنشاء المدير الوحيد.

```sh
npm test
npm run build
npm run typecheck
npm run start
```

اختبارات المتصفح: `npx playwright install chromium` ثم `npm run test:e2e` بعد البناء. تستخدم قاعدة منفصلة مؤقتة ولا ترسل إشعارات حقيقية. في بيئة cloud الحالية Chromium مثبت بالفعل؛ استخدم `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:e2e`، و`npm --cache /tmp/testcodex-npm-cache ci` عند إعادة التثبيت. لا حاجة لتنزيل متصفح إضافي.

## معاينة الواجهة على GitHub Pages

لنشر لوحة فعلية بخدمات مجانية، استخدم [نسخة Cloudflare Workers وD1](cloudflare/README.md). تستضيف الواجهة وAPI والحملات المجدولة على Worker واحد. تحتاج Database ID الحقيقي وأسرار Firebase في إعدادات Worker؛ معاينة GitHub Pages منفصلة عن هذه اللوحة.

يمكن نشر واجهة تطبيق الاختبار مجانًا عبر workflow في `.github/workflows/pages.yml`. راجع [خطوات تفعيل GitHub Pages](mobile/GITHUB_PAGES.md). المعاينة تدعم المحاكاة المحلية فقط؛ لوحة الحملات وقاعدة بياناتها وإرسال FCM تحتاج خادمًا منفصلًا.

## Firebase Cloud Messaging — الخيار الافتراضي

1. أنشئ مشروع Firebase وفعّل Cloud Messaging API HTTP v1.
2. أضف Android و/أو iOS إلى المشروع؛ iOS يحتاج مفتاح APNs في إعدادات Firebase.
3. جهّز حساب خدمة بصلاحية إرسال رسائل FCM. احفظ JSON خارج المستودع، واضبط `GOOGLE_APPLICATION_CREDENTIALS` لمساره المطلق، أو احقن `FCM_SERVICE_ACCOUNT_JSON` كسرّ على الخادم. البيانات يجب أن تكون حقيقية في عملية Node لأنها تُستخدم لتوقيع JWT محليًا؛ placeholder من proxy لا يكفي.
4. في تطبيقك، اطلب إذن الإشعارات، احصل على FCM token، وأرسله إلى خادم تطبيقك. أعد التسجيل عند تغيير الرمز.
5. خادم تطبيقك يرسل طلب تسجيل الجهاز للوحة. عالج `data.url` عند فتح الإشعار إذا أردت الانتقال لشاشة محددة.

الوجهات المطلوبة للإرسال: `oauth2.googleapis.com` و`fcm.googleapis.com`. لا تختبر صلاحية المزوّد بإرسال حملة لجمهور فعلي دون قصد. استخدم جهاز اختبار وشريحة مخصصة لأول إرسال.

## Expo (اختياري)

اضبط `PUSH_PROVIDER=expo`، وسجّل Expo Push Tokens بدل رموز FCM. إذا فعّلت enhanced push security، اضبط `EXPO_ACCESS_TOKEN` على الخادم. يحتاج الاتصال إلى `exp.host`. يلزم إعداد credentials الخاصة بالمنصات داخل مشروع Expo.

## تسجيل الأجهزة

اضبط `CMS_DEVICE_API_KEY` بمفتاح عشوائي بطول 32 حرفًا أو أكثر، مشترك بين خادم تطبيقك وخادم اللوحة. يمكن توليده محليًا باستخدام `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`، ثم تخزينه بأمان؛ لا تضعه في تطبيق الموبايل أو Git.

```http
POST /api/devices
Authorization: Bearer <server-api-key>
Content-Type: application/json

{"token":"<device-push-token>","platform":"android","segment":"customers"}
```

`platform` هو `android` أو `ios`. اسم الشريحة 1–64 حرفًا من الأحرف الإنجليزية والأرقام و`_` و`-`. استخدم `all` في الحملة لاستهداف كل الشرائح. الجهاز ينتمي لشريحة واحدة في هذه النسخة. إعادة تسجيل نفس الرمز تحدّث الشريحة والنظام وتعيد تنشيطه. `DELETE /api/devices` مع `{"token":"..."}` يلغي الاشتراك. خادم تطبيقك مسؤول عن التأكد من هوية المستخدم وأذونات الاشتراك قبل تمرير التسجيل، وإلغاء التسجيل عند الخروج/إلغاء الموافقة.

## التشغيل والإرسال

احفظ الحملة أولًا، ثم اضغط «إرسال الآن» وأكد الإرسال. الجدولة تحفظ الوقت بصيغة UTC؛ الإدخال بتوقيت جهازك. العامل يتحقق كل 30 ثانية، ويجب أن يبقى شغالًا بجانب الويب، وبنفس إعدادات المزوّد ومسار قاعدة البيانات. بدون المزوّد أو جمهور نشط، تبقى الحملة المجدولة بانتظار المتطلبات.

تُقفل الحملة ذريًا قبل الإرسال لمنع تكرار إرسالها من العامل والواجهة. لا تعاد المحاولة تلقائيًا عند فشل شبكة مبهم لأن المزوّد قد يكون قد قبل الطلب. إذا توقفت العملية أثناء إرسال حملة، تبقى `sending` للمراجعة اليدوية؛ لا تغيّرها إلى مسودة وتعيد إرسالها للجميع دون التحقيق. الحالات النهائية غير قابلة للتعديل أو إعادة الإرسال؛ أنشئ حملة جديدة عند الحاجة.

«طلبات مقبولة» تعني قبول FCM أو حصول Expo على ticket، وليس إثبات الوصول أو الفتح. لا يوجد حاليًا تتبّع فتح/وصول أو فحص Expo receipts. لا يوجد إرسال تلقائي عند تسجيل الأجهزة.

## حدود النسخة الأولى

مدير واحد، شريحة واحدة لكل جهاز، إرسال دفعات بتوازي 10، قاعدة SQLite مشتركة محلية وعامل مستمر. هذه نسخة أولى وليست نظامًا موزعًا لحملات ضخمة. للنشر واسع النطاق يلزم طابور مهام متين، صلاحيات متعددة، سياسات احتفاظ، تتبّع ومراقبة، وعزل الجمهور حسب التطبيق. الإرسال اليدوي يجري ضمن طلب الخادم، فلا يناسب حدود التنفيذ القصيرة في serverless.

انشر على Node.js بخادم مستمر وقرص دائم، واضبط `CMS_SECURE_COOKIES=true` مع HTTPS. احتفظ بنسخ احتياطية متسقة لSQLite باستخدام أداة backup الخاصة بها؛ لا تنسخ ملف القاعدة وحده أثناء الكتابة في وضع WAL. `.data/` و`.env*` مستثناة من Git. لا تضع بيانات حساب خدمة في المستودع. احمِ `/setup` أثناء إنشاء المدير. الاختبارات تثبت المنطق المحلي والواجهة؛ الإرسال إلى جهاز فعلي يحتاج بيانات مزوّد وتطبيقًا مسجلًا ولم يُختبر في هذه البيئة.

كل مهمة cloud معزولة؛ استخدم checkout الحالي ولا تنشئ Git worktree دون طلب صريح.

## تطبيق Android التجريبي

أضيف تطبيق React Native في [mobile](mobile/README.md)، مع معاينة للواجهة دون Firebase. صفحة الأجهزة والجمهور تولّد رمز ربط مؤقتًا ليسجّل التطبيق جهازًا في شريحة `test` دون تضمين مفتاح الخادم. راجع دليل التطبيق لمتطلبات Firebase وطريقة البناء والتمييز بين المحاكاة والاستقبال الفعلي.
